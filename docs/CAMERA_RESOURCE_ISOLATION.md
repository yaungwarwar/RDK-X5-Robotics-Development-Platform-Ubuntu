# Phase B.1 camera laboratory isolation review

Status: **one bounded metadata-only subscription and one short left-camera preview have run**. On 2026-11-25 the RDK X5 exposed cgroup v2 and an available user systemd manager. A short-lived, user-owned `systemd-run --user --scope` probe ran only `/usr/bin/python3`; it did not start a camera, laboratory broker or image subscription. With `MemoryMax=384M`, `MemorySwapMax=0`, and `TasksMax=64`, the probe observed `memory.max=402653184`, `memory.swap.max=0` and `pids.max=64` inside the transient scope. A separate probe requesting `CPUQuota=50%` found **no `cpu.max` file** in the scope; user-slice delegated controllers were `memory pids` only. Thus there is no verified cgroup CPU-rate limit. `LimitCPU=` is not accepted as a scope property on this host; a later scope probe using `prlimit --cpu=15:16 --nofile=128:128` observed RLIMIT_CPU 15/16 seconds and RLIMIT_NOFILE 128/128. The scope was transient and exited. No kernel, Docker, watchdog or existing service settings were changed.

The user separately approved one narrowly bounded preview after an existing camera publisher was confirmed: a fresh lab-only user scope with combined 384 MiB memory, zero swap and 64 tasks; per-process inherited CPU-time and file-descriptor limits; reduced scheduling priority; an external short wall-clock deadline; and active monitoring of v0.1.3 health, temperatures and actual process usage. RLIMIT_CPU limits **cumulative CPU time per process**, not CPU rate or aggregate usage; nice is not a CPU cap. The scope's memory and task limits cover broker and child together, not independent budgets. OOM or CPU-time termination can end the test and its actual effect on middleware requires measurement. These limits cannot bound kernel DDS resources or the remote browser's decode memory, and no real camera workload has validated their sufficiency. Do not infer reliable real-time isolation or proceed solely from the probe. Any further physical preview or target update requires renewed user authorization.

The Phase B application additionally caps raw input at 1280×720 / 2,764,800 bytes, output and IPC payload at 2 MiB, one native worker and latest slots, QoS depth one, and browser ACK/send deadlines. Raw image buffers may already be allocated by ROS/DDS before Python validation. The physical left frame measured 1088×1280 NV12, stride 1088, 2,088,960 bytes. After the mismatch was reported, the user approved a height-limit correction to 1280 for NV12; the 2,764,800-byte raw cap and 2 MiB IPC cap remain unchanged. The NV12 correction was transferred and delivered 17 physical preview frames; reconnect was not successful in that session.

A single metadata-only left image and calibration subscriber was run in the above memory/task-limited scope with `prlimit --cpu=15:16`, lower priority, a 25-second external deadline, and an internal 75 °C / health stop threshold. It received three messages and one camera_info, then destroyed its node and exited. Scope memory peak was 44,679,168 bytes, task count at sample 18, and process CPU time 2.682 seconds; one health sample was healthy and both reported thermal zones were 72.992 °C. This is not a sustained load measurement. A post-test check found no lab worker and healthy v0.1.3. The user later approved one physical preview of the NV12 correction; that 30-second-limited session has ended and additional physical testing or target updates require renewed authorization.

The approved preview stayed within the verified memory/task scope and left no worker or lab listener after the wall-clock deadline. It exposed an immediate reconnect race, reproduced and corrected on the workstation. The corrected bundle was later transferred and verified, but its reconnect behavior has not been physically validated. See [resource report](CAMERA_PHYSICAL_RESOURCE_REPORT.md).

The first authorized attempt to physically retest the reconnect fix established the same memory/task limits and listener ownership but was stopped before subscription at 74.604 °C preflight, less than 0.4 °C below the 75 °C stop threshold. The user was asked to arrange cooling and separately authorize a fresh bounded attempt; the lack of a CPU-rate quota remains unchanged.

A later authorized reconnect attempt had the stricter user precondition of CPU and DDR at or below 73 °C for 60 seconds. Its first sample exceeded that bound (CPU 74.067 °C, DDR 74.116 °C), so no new scope or subscription was started. The existing 75 °C stop threshold and all cgroup/kernel/systemd settings remained unchanged.

After a reboot, one 61.91-second temperature interval met the user's ≤73 °C precondition, but the immediate scope preflight rose to DDR 73.285 °C / CPU 73.041 °C. The guard exited before launching the scope or subscribing; a further 121.88-second observation found no new qualifying interval. This does not validate reconnect or CPU isolation.

The user has since suspended physical testing until they confirm continuous active cooling has been installed. Do not automatically repeat thermal monitoring. See the [local engineering review](CAMERA_LOCAL_ENGINEERING_REVIEW.md).
