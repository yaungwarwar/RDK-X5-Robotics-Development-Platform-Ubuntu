# Release reproducibility plan

This is a proposal, not a release, deployment or claim of bit-for-bit reproducibility. Preserve the original v0.1.3 archive and manifest and all existing transactions. Do not overwrite completed transactions or verified laboratory bundles.

1. Establish reviewed source history and a signed release reference; record commit, dirty state, submodules, build inputs, toolchain, architecture and build commands. Generate and verify a complete source manifest before building. Store build attestations and artifacts separately from secrets and target-specific records.
2. Replace floating Docker base-image tags with reviewed immutable digest references. Record both the multi-architecture manifest-list digest and the resolved ARM64 image digest; verify target architecture, image provenance and vulnerability status. Pinning is a future change requiring compatibility testing.
3. Lock every direct and transitive Python dependency per supported Python version and architecture, including environment markers and hashes. Verify wheels with `pip --require-hashes`; generate separate ARM64 and workstation lock sets where necessary. Preserve licenses and provenance. Do not treat current version pins as hash locking.
4. Build an ARM64 wheelhouse in a controlled environment and verify hashes, native ABI tags, dependency closure and Python 3.10 compatibility. Rehearse offline isolated installation using `--no-index --find-links` with no vendor-package mutation. Current workstation wheels do not prove ARM64 offline feasibility.
5. Produce archives deterministically where tools permit: normalize ordering, timestamps, ownership and compression metadata; compare two clean independent builds. If a dependency prevents bit reproducibility, identify and record the non-determinism instead of asserting equivalence. Publish checksums, manifests and provenance without secrets; never replace an existing versioned archive.
6. Define and test explicit supported source-to-target migrations, including the planned v0.1.3 to v0.2.0 path, and reject untested versions rather than guessing. Preserve automatic resolution of the active generated Compose profile and established security limits. Validate ARM64 dependencies, image identity, space, transaction state and systemd compatibility before activation.
7. Rehearse prepare, apply, health validation and recovery using fresh isolated transactions and verified stable recovery scripts. Restore exact source, isolated venv, image and active Compose profile; verify security protections and service health. Local simulated rollback is not physical rollback. A physical rehearsal requires its own safe window and approval.

Additional systemd hardening is a planned compatibility study, not an instruction to change the installed protections. The dedicated sensor fault, unavailable verified CPU-rate quota, authentication/TLS absence and target thermal margin remain separately tracked in the [findings register](ENGINEERING_FINDINGS_REGISTER.md).
