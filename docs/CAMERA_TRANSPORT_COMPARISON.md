# Camera transport comparison — Phase A

Decision: use **binary WebSocket frames with one explicit client acknowledgement per frame**, and a latest-frame slot, for the synthetic laboratory prototype. Evaluate the same pattern for future local JPEG previews only after native measurements. The laboratory currently sends generated SVG bytes, not JPEG, ROS messages or camera data. Binary frames avoid base64 expansion; metadata travels in a separate JSON message. The ACK is essential: ordinary browser WebSocket has no built-in receive backpressure ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)).

| Option | Complexity and dependencies | Memory, bandwidth, backpressure and isolation | Suitability |
|---|---|---|---|
| MJPEG over HTTP | Simple browser `<img>` and JPEG source; separate metadata/control channel needed | Each client may buffer; proxy buffering and disconnect handling need explicit limits; JPEG per frame can cost bandwidth and CPU; worker isolation still necessary | Viable fallback for simple previews, but client-side per-frame acknowledgement and metadata are less direct |
| Binary WebSocket | Existing browser and FastAPI stacks; small framing and control protocol | One outstanding frame with ACK, bounded latest slot and timeout provide application-level backpressure. Payload and client limits required; socket buffers and browser decode memory still need measurement | Selected for local lab: explicit lifecycle, frame age, counters and switching; no new streaming framework |
| Existing ROS2 compressed publisher | Input source, not a browser transport. May avoid local JPEG encoding only if actual topic/type/format is compatible | Can reduce conversion CPU and raw bandwidth, but source rate, DDS buffers and image sizes remain bounded separately | Prefer as an input only after physical topic, publisher, format and QoS verification; do not assume `/image_combine_jpeg` exists |
| WebRTC | Browser media support and adaptive video; signalling, codecs, transport and deployment complexity | Potentially efficient for sustained video, but encoder, buffers, ICE and memory add operational/security work. ARM64 codec availability must be measured | Excessive for the first loopback laboratory preview; reconsider if measured needs justify it |
| GStreamer | Flexible pipelines and ARM64 packages/plugins, possibly hardware codec support | Pipeline queues and codec buffers must be bounded; plugin, ABI, vendor integration and process failures require isolation | Optional future experiment, not a dependency of this phase |

JPEG has broad browser support ([MDN image formats](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types)); actual browser/ARM64 and codec performance must still be measured. [GStreamer webrtcbin](https://gstreamer.freedesktop.org/documentation/webrtc/) supports signalling and transport machinery, illustrating additional integration rather than proving hardware suitability. ROS2 [Image](https://raw.githubusercontent.com/ros2/common_interfaces/humble/sensor_msgs/msg/Image.msg) carries width, height, encoding, stride and data; [CompressedImage](https://raw.githubusercontent.com/ros2/common_interfaces/humble/sensor_msgs/msg/CompressedImage.msg) describes compressed payload and format. Names do not establish message types. The native worker must validate exact size/stride, dimensions, encoding, timestamps and bounded memory before conversion. Unsupported or malformed data must be dropped, not guessed.
