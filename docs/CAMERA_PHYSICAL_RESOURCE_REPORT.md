# Physical camera laboratory resource report

> Historical operator evidence: review and redact target-specific details before publication.

On 2026-11-25, before the user started the camera, v0.1.3 native health was `ok` with a fresh collector and null error; the dashboard was healthy. Root filesystem had 45 GiB available; memory was 7080 MiB total and 6276 MiB available; swap was 0 MiB. CPU and DDR were approximately 58.434 °C and 59.460 °C. After the user started the camera, the initial metadata-only probe saw both zones at 72.992 °C, a healthy service, scope memory peak 44,679,168 bytes, 18 current tasks and 2.682 seconds of process CPU time. These are point observations.

A separate user-approved, 30-second-deadline left-camera preview ran in a transient user scope with combined `memory.max=402653184` bytes, `memory.swap.max=0`, and `pids.max=64`. The scope had **no `cpu.max`**. Each process inherited RLIMIT_CPU 15/16 seconds and RLIMIT_NOFILE 128, and ran at reduced priority; these do not impose a CPU-rate quota. Initial broker-only scope RSS accounting was about 31–32 MiB; the observed scope peak was **83,931,136 bytes** (~80.0 MiB). Worker RSS reported in frame metadata ranged **61,568–68,812 KiB**, and measured worker CPU intervals **97.73–116.09% of one core**. These are short, sampled observations, not a stable benchmark. Nginx/dashboard and native telemetry stayed healthy in sampled checks. The selected 75 °C stop threshold was not observed to be reached; output included a 74.165 °C reading, but complete peak temperature was not retained, so no exact maximum is claimed.

The first preview delivered and browser-decoded 17 binary frames; session metadata reported delivery up to 4.47 fps, payload rate up to 3,255,908 bytes/s, broker residence age mostly 1–3 ms with one 73 ms sample, and zero broker/worker drops and invalid-frame reports. Those age values omit acquisition-to-broker and browser decode/transit time. Source publisher rate was not measured reliably. The test then exposed an immediate-reconnect race, so reconnect was not accepted. At the 30-second deadline the scope stopped, the lab listener and worker disappeared, image and camera_info subscriber lists were empty, and the user-started camera processes remained running. Post-test v0.1.3 health was `ok`; dashboard healthy, original unit hash unchanged, and listeners stayed on 127.0.0.1. Long-duration stability, color, right/combined views, sustained FPS and complete lifecycle acceptance remain pending.

Creating a second independent venv under the 15/16-second per-process CPU-time limit failed in `ensurepip`; the scope recorded 15.971 CPU seconds. The failed directory was retained. The test used the previously created separate lab venv, which had `include-system-site-packages = false` and passed `pip check`; it did not use the installed application's venv. See [isolation review](CAMERA_RESOURCE_ISOLATION.md) for the missing CPU-rate limit and further caveats.

A separately authorized reconnect retest was prepared in a fresh directory. Its lab-only scope confirmed `memory.max=402653184`, `memory.swap.max=0`, `pids.max=64`, no `cpu.max`, and owned loopback listener. Preflight CPU/DDR readings were both 74.604 °C. Because that left less than 0.4 °C below the 75 °C stop threshold, the agent stopped the lab scope before any image subscription or worker startup. No threshold crossing was observed; no corrected reconnect or load result was obtained. Afterward CPU/DDR were 73.921/74.116 °C, v0.1.3 was healthy, the lab scope inactive, and the camera PIDs remained running. Additional testing requires the board to cool and explicit authorization for a new bounded scope.

A later separately authorized retest required both sensors to remain at or below 73 °C for 60 seconds. The first sample was DDR 74.116 °C and CPU 74.067 °C, so the precondition failed immediately; no 60-second qualifying interval was established. No new preview, worker or subscription was started. The v0.1.3 backend and dashboard were healthy, the previous lab scope was inactive, port 18100 was free, and the user-started camera processes remained present. These readings do not show a 75 °C stop-threshold crossing.

After the user rebooted and restarted the camera, a 61.91-second sampled interval met the ≤73 °C requirement (DDR 71.869–72.846 °C; CPU 71.429–72.748 °C). The immediately subsequent preflight had already risen to DDR 73.285 °C / CPU 73.041 °C, so the retest guard exited before starting the scope or subscribing. A further 121.88 seconds of read-only monitoring did not establish another qualifying interval. Final readings were DDR 73.676 °C / CPU 73.383 °C; the existing camera and v0.1.3 remained running and healthy, with no lab worker or listener. No reconnect resource figures are available from this attempt.
