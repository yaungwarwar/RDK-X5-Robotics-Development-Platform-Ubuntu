# GS130WI physical compatibility — observation and pending checks

On 2026-11-25, after user approval for a stationary bench session, read-only SSH inspection found the RDK X5 on ARM64/Python 3.10.12 with healthy native v0.1.3 and a healthy dashboard. Native `/usr/bin/python3` successfully imported `rclpy`, `sensor_msgs.msg.Image`, `CompressedImage` and `CameraInfo` after sourcing the installed TogetheROS setup. The existing monitoring graph reported successful discovery, zero failures and only its monitor node plus `/parameter_events`; separate `ros2 node list --no-daemon --spin-time 2` returned no nodes, and `ros2 topic list -t --no-daemon --spin-time 2` returned `/parameter_events` and `/rosout`. No GS130WI image or camera_info publisher, message type, publisher count or offered QoS could be confirmed. A vendor `cam-service` process existed but is not evidence of an active ROS camera publisher. The user was asked to start the existing camera application manually; the agent did not launch one.

The earlier reported 1088×1280 camera configuration is historical, not a current measurement. It would exceed the lab's 720-pixel height bound. If RGB8 were actually used, a tightly packed 1088×1280 image would be 4,177,920 bytes, above the raw cap of 2,764,800 bytes; this is a conditional calculation, not an observation. Actual width, height, encoding, stride, payload, calibration, QoS, publisher counts and JPEG availability remain **unmeasured**. Supported lab raw encodings are rgb8, bgr8 and mono8, and compressed JPEG/PNG are structurally checked; no currently observed camera format can be classified as supported or unsupported. No image subscription or compatibility correction was made.

## First physical metadata-only sample

The user manually started the existing GS130WI application and explicitly authorized bounded read-only subscriptions. The graph then showed `/mipi_cam` with one publisher each for `/image_left_raw`, `/image_right_raw`, `/image_combine_raw` (`sensor_msgs/msg/Image`) and their four corresponding camera_info topics (`sensor_msgs/msg/CameraInfo`). All seven offered RELIABLE/VOLATILE QoS; discovered history/depth were UNKNOWN/0. `/image_combine_jpeg` had zero publishers. RELIABLE offered and BEST_EFFORT requested are compatible in principle, and the left metadata-only subscription did receive data; other views were not subscribed.

Three left image messages reported **1088×1280**, encoding **`nv12`**, stride **1088**, and **2,088,960 bytes** each. No image bytes were printed or retained. The left camera_info reported 1088×1280, frame ID `default_cam`, empty distortion model, K `[514.505615234375, 0, 500.24566650390625, 0, 514.505615234375, 592.1663208007812, 0, 0, 1]`, and D `[0, 0, 0, 0, 0]`. Header stamps were around 9650 seconds while host epoch time was around 1795586448 seconds; they resemble host monotonic uptime but clock provenance is **not established**, so do not calculate wall-clock capture latency from them. Three messages over a short burst are insufficient to establish a sustained received FPS. No preview was started, so delivered FPS, actual decode, frame ages and drops remain unmeasured.

The original worker rejected NV12 and 1280 height. After reporting those measurements, the user explicitly approved a **local-only** correction. The workstation worker now permits NV12 up to 1280×1280 with even dimensions/stride and exact 3/2-plane byte length, retains the prior 2,764,800-byte raw ceiling and 2 MiB output/IPC ceiling, and encodes only the Y plane as an explicitly labelled **grayscale luminance** PNG. The original 720-pixel limit remains for other raw formats and compressed images. The standalone broker accepts the larger output and the UI identifies the grayscale rendering. Synthetic fixtures use the observed metadata, not saved physical image data. The NV12 luminance correction was subsequently transferred into a new standalone lab directory with separate approval and did deliver browser-decoded left frames. Immediate reconnect failed because the previous worker had not finished stopping; a further correction was made locally and has not yet been physically validated. Combined/right dimensions and sustained hardware throughput remain unknown.

The observed left grayscale preview produced 17 browser-decoded frames with source encoding nv12 and displayed 1088×1280 and calibration. Last reported delivery was 4.47 fps and 3,255,908 payload bytes/s, with zero reported broker/worker drops or invalid frames in that short session. Full RGB color was not rendered. Source header timestamps were not shown to share a clock domain with wall time. No right/combined preview or JPEG publisher was tested.
