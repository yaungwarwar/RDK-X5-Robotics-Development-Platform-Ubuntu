# Source history recovery and reconciliation plan

This is a read-only assessment and proposal. No Git repository was initialized, committed, pushed, reset, or assigned a remote during B.4.2. In the current execution environment the workspace's visible `.git` directory has no usable repository metadata. Its origin cannot be determined from that fact alone. A sibling workspace ZIP exists but contains environments and caches and is not a clean source archive. Preserved v0.1.2/v0.1.3 archives and source manifests provide historical release evidence, not complete development history.

The previously created temporary publication checkout at `a temporary local checkout` is a separate Git repository at commit `2feb5bebb62d292c5e2234383fa5dec2f4431cf0`; it is not the workspace and may disappear. A local Git-blob comparison against its 180 tracked files found **two modified files and no missing tracked files**: `docs/CAMERA_LOCAL_RESOURCE_BENCHMARK.md` and `docs/V0.2.0_PHASE_B2_COMPLETION.md`. Their changes are workstation-specific command paths retained locally and replaced by configurable variables in the published copy. No additional non-generated project files were found before beginning B.4.2; the new B.4.2 reports are subsequent documentation. The changed built lab asset in the previous release is already represented in this Git baseline. This comparison is local and makes no claim about a subsequently changed remote.

Generated or local-only material includes `frontend/dist`, generated lab build assets (the latter are deliberately part of the standalone bundle), screenshot outputs, `qa-results/`, `__pycache__`, test/lint caches and TypeScript build caches. Private operational evidence includes physical acceptance records, host-specific paths/addresses and transaction details; original incident evidence and operator records should remain private. Virtual environments, `.venv-qa-tools` (including SSH keys), wheel caches, node_modules, downloaded tools, backups, `.env`, credentials and raw images must never be committed. Existing release archives/manifests are immutable historical artifacts and require deliberate release handling, not regeneration.

The accepted source itself contains target-specific installation account/path literals and mock addresses matching the historical target. The user explicitly permitted these existing source/test literals **for private archival preservation only**. They are preserved byte-for-byte in the private checkpoint; private operational records and evidence remain excluded. A future publication artifact must be separately sanitized, manifested, compared and validated; do not call it byte-identical to the private checkpoint. Keep exact working source and private incident evidence intact. See [baseline preservation](B41_BASELINE_PRESERVATION.md).

After separate approval, establish a durable repository in a new location using the reviewed known Git baseline, preserving its full history. Compare its tracked and untracked files against this workspace, resolve the two intentional documentation redactions, review all B.4.2 documentation and generated/ignored files, then apply only reviewed changes. Check secrets and private operational data, verify source manifests and all existing immutable artifacts, and have the owner review the resulting diff before any commit or remote change. Never overlay the existing workspace or treat the temporary checkout as complete historical provenance. See [release reproducibility](RELEASE_REPRODUCIBILITY_PLAN.md).
