# v0.2.0 roadmap — planning only

The proposed next cycle adds opt-in, read-only live stereo visualization for RDK X5 and GS130WI. The v0.1.x work is documented with physical rollback, active-camera publisher checks and dynamic BPU inference checks outstanding; a safe window and appropriate authorization are required for those checks. These limitations must inform next-phase planning.

1. Define the ROS2 image transport integration and compatibility against the existing camera publishers. Never launch a duplicate camera capture process. Discover calibration metadata and report resolution and measured frame rate without assuming a publisher is present.
2. Provide left, right and combined views and show available calibration information. User-controlled activation must be explicit; subscriptions start only for requested streams and stop promptly when no longer needed, including disconnect, navigation and failure paths.
3. Bound queues, buffering, frame size, work and subscriber lifetime; define backpressure and stale-frame behavior. Measure backend and frontend resources and network bandwidth under representative approved workloads, with explicit limits and observable overload.
4. Validate responsiveness, security, reconnect and lifecycle behavior without altering vendor cameras, DDS settings or systemd protections. Preserve the existing non-root, read-only container, dropped capabilities, loopback bindings and systemd hardening. Evaluate authentication and TLS separately before any remote exposure.

Detailed architecture, transport choices, performance targets and a hardware test plan remain to be designed. This roadmap does not authorize implementation or new camera processes.

Carry forward the dedicated BPU temperature sensor errno 110, QA-INFRA-001, the fixed systemctl subprocess output-size limitation, missing authentication/TLS, and repeated ROS2 subprocess startup overhead. Address these only through separately authorized planning and development.
